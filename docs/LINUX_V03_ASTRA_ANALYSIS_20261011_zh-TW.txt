三、演算法、資料流與可以支持的結論

1. 來源與佇列
main.cpp:360–375 的 producer 以固定目標 period 擷取，以來源 i 產生圖樣；
include/msu2/latest.hpp:13–24 只保留一張等待影格，正在傳送者不會被覆蓋。
來源 ID 缺口會依當時 active epoch 映射成各區 missed_queue，而非悄悄重新排列輪次。
在持續過載時，固定倍數的來源缺口仍可能反覆命中同一個 phase，導致某區很久輪不到。
這是本次來源時槽定義下可觀察的失敗狀況；不能用「沒有 intentional skip」推論沒有飢餓。

producer 若擷取本身超過 period，會把下一次 deadline 重設到當下；它不是硬即時時鐘，
也沒有為未曾產生的時間槽補造 frame_id。跨機效能比較必須同時保留實際產生時間與來源數。

2. 參考畫布
主機 committed 是最近成功傳送的全幅合成畫布，各區可以來自不同來源 ID。
main.cpp:191–218 比較／提交區域；分區成功後以 committed 更新 DeltaPlanner；
恢復正常 diff 時比較的是這張合成畫布，能補齊仍舊的區域，不會把未傳側區假裝已完成。
unchanged 表示所選區與主機參考逐像素相等，沒有發送 window；不是成功傳送一幀。
來源比對使用 RGB565，故 RGB888 有變不一定形成新的裝置像素值。

Session.send 完成只表示既有開窗 ACK 和主機 write_all 路徑完成。對區域外保留像素、
LCD 完成時刻與畫面品質仍須實機驗證。任一後段 patch 失敗，裝置可能已收到前段 patch；
主機 invalidate／停止可避免沿用不確定參考，不能把已傳出的畫面回滾。

3. 成本模型與切換
priority.cpp:53–73 的 EWMA alpha=0.25，把成功傳輸分解成每個 18-byte window 的
開窗／ACK 主機時間，以及每 payload byte 的主機寫入時間，再加當前擷取與準備時間。
它是主機成本啟發式，不是 USB bus 吞吐或 LCD 處理速度的量測。

進入條件是原方案預估 >=85% period，或前次實際忙碌 >=95%，或發現新 queue drop。
退出需要連續至少 max(fps,20) 個安全觀察、在分區至少 1000 ms，並同時滿足原方案
預估 <=60%、前次實際 <=70%、沒有新 drop；若 keyframe 到期，該全幅本身的預估也須
<=60% period 才可累積安全觀察，並在 dwell／streak 達標時退出。
依據 priority.cpp:126–153。README 所稱「低於」應按程式的 <= 邊界解讀。

capture_ms 在 producer 測得、傳輸在 consumer 執行；相加是保守的總工作量指標，
不是兩執行緒管線臨界路徑的精確估算。driver buffer、ACK 固定成本、chunk 次數與
頁面壓縮率都會讓線性 byte 外推失準。每輪先算完整 full/diff 再算區域，也沒有免除
完整規劃的 CPU 成本。閾值必須以 Linux 實測校準，不能當設備能力規格。

4. raw 成本作為核對基線
依 src/protocol.cpp:32–71，不含回覆資料的 raw 成本為 18 + 390×ceil(像素數×2/256)。

送出範圍       單次 wire bytes    每輪全部區域 wire bytes
160×80 full       39,018                  39,018
160×20 bands       9,768                  39,072（4 區）
80×80 halves      19,518                  39,036（2 區）
center3          19,518／9,768             39,054（中／左／右）

分區縮短一次佔用並降低各區更新頻率；完整一輪總 bytes 不會因切割而下降。
pair 仍在完整 256-byte 頁中找重複四-byte 組，並非跨幀差分；噪聲通常接近 raw，
只改少量但分散像素也可能需要每區整片重送。不能把 1% 來源變動直接當成 1% 傳輸量。

四、本次找出的缺陷及修正覆核

A. 到期 keyframe 被吞掉：初版實際缺陷，最後原始碼與新增重測均已核對。
初版 main.cpp 以 last_full 判斷 keyframe，將 full_plan 強制全幅後交 scheduler；
active 分區卻丟棄該計畫改傳一區，last_full 只在正常全幅成功後更新。
當 forced-full 預估一直 >60% period，即使來源靜止且各區已相等，safe_count 仍無法
累積；unchanged 又不更新 estimator，故可永久停留分區，定期 full 也一直未真正送出。

修正版 main.cpp:390–409 以未強制的正常 full/diff 估值判斷恢復；到期則另建 full。
:418、434 使 keyframe 不受區域替代或 side skip；成功 commit 整張、更新 last_full；
priority.cpp:146–153 要求到期全幅本身也夠安全，:211–221 在維持分區時保留 active/epoch，
僅原排定區 due/sent +1，
但所有區同步來源 ID 與時間。新成本仍回饋 actual／EWMA，慢 full 不會被視為輕量更新。
CSV 用 priority_keyframe_full 識別實際全幅，region/region_slot 仍代表原排定時槽；
閱讀者不能將該行 region 名稱當成實际 wire 矩形。

本代理也覆核了修正中的短間隔邊界：若 keyframe_ms 小於來源間隔，可能每槽都到期；
不能用 maintenance_full 布林值無條件阻止退出。最後改為普通計畫與到期全幅各自預估，
兩者都安全才能累積 streak，因此每槽都是低成本 full 也仍可正常恢復，昂貴 full 則重設 streak。

「有界」是指到期後下一個被處理來源即嘗試 full，不是保證每 keyframe_ms 毫秒準時
完成。in-flight 工作、來源排程、I/O timeout 或程序結束都會影響時刻；失敗應停止。

B. center3 無新樣本造成側區停滯：已加入受限探測並有新增離線回歸證據。
初版一次慢 ACK 可使側區預估永久高；若後續中央 unchanged、左右持續變動且 keyframe=0，
左右全部 skipped，沒有成功傳輸樣本能更新 EWMA。刷新 actual_busy 本身解不開這個迴圈。
修正版 priority.cpp:167–184 在側區距上次主機同步 >=1000 ms、且前一時槽實际 <=70%
時允許探測；前一 actual >=90% 仍拒絕。成功探測可帶回新樣本並重設該側同步時刻。

這是「舊估值時有限度重新嘗試」，不是已證明保住中央的排程保證。
程式只檢查前一時槽低忙碌，不是連續一秒低忙碌；1000 ms 是側區同步年齡。
如果真正鏈路仍慢，探測可能阻塞後續中央並導致 queue misses，必須讓統計顯示此代價。
現階段勿把這個常數視為最佳值，亦不得藉探測隱藏 dropped/missed_queue。

C. 失敗紀錄與 no-commit：已加 adaptive_failure；仍有明確觀測邊界。
初版 failed counter 在 throw 後沒有輸出機會，CSV 和末尾摘要均看不到它。
修正版 main.cpp:472–491 先 invalidate，再以 stderr 留下 frame、layout、原排定區、
failure phase、ACK timeout 類別、已完成 Session.send bytes、當下 queue replacement。
成功 CSV 不納入不完整更新，維持其完成時槽語義，這個分離是合理的。

completed_wire_bytes 只加計已返回成功的 patch；失敗 patch 的 18-byte window 或部分
payload 可能已送出卻不在此欄。此欄不是全部已接受 bytes，也不是線上總流量。
keyframe 失敗事件的 region 是被替代的原排定區，不能單憑這個欄位推論失敗窗口尺寸。
Session::wait_pattern（src/session.cpp:24–39）仍不保留 timeout 收到的 MSN／部分回覆；
新分類不能判定 ACK 缺失的裝置根因，也没有加入握手、恢復或原始 RX trace。

D. max_stale_ms：模式退出間隔已補；指標定義應保持克制。
修正版 priority.cpp:124 在每次可觀察來源更新所有 active 區年齡，:228 在正常更新
重設同步時間前先結算。維護 full 也先記各區間隔再重設。
這是截至觀察點的「距主機最後確認相等／成功送出最大間隔」，不是像素確實錯誤的持續
時間或 LCD latency；靜止來源的 unchanged 同樣可以推進同步時刻。
程序最後一個觀察點之後、join／結束的尾段不會自動成為區域樣本，勿擴大其時間範圍。

六、仍需保留的風險與範圍

1. 原生 Linux 與實機均未驗證。現有 executable 是 Mach-O arm64；build.sh 使用當地 C++
compiler，不是 Linux cross-compile。CMake 的 CTest 只掛 core/delta/priority，PTY 必須另跑。
最後 PTY footer 已改由 platform.system()/machine() 動態報告實際平台，修正初版固定
macOS 字串的證據標籤問題；本次仍顯示 Darwin arm64。CMake 路徑本次沒有執行驗證。

2. SessionOptions::write_chunk（include/msu2/session.hpp:11）仍為 3840，CLI 覆蓋成 60。
對現有 CLI 不是錯誤；其他程式直接建立 Session 的預設不同。現有 core fast_options
明確設 60，不能防止這個 API／CLI 差異。需在使用 library API 時明確指定或統一預設。

3. 初握手 echo、orientation、window ACK 的底層 wait_pattern 共用通用 timeout 字串。
adaptive_failure 只對進入串流後提供上下文；未來原生診斷仍需要明確 operation phase、
有限長度 RX 原始資料、write 進度與 errno，才能分辨握手失敗、window ACK timeout、
payload write timeout、disconnect，以及無任何 I/O 的排程 skip。

4. timeout 不是整個 update 的單一 end-to-end 上限。Session::send 對 window write、
ACK wait、payload deadline 各使用預算；多矩形 deadline 只在下一個 patch 開始前檢查。
既有程序仍會失敗退出，但不能把 --timeout-ms 2000 解讀為整次更新一定在 2 秒內返回。
這是沿用 v0.2 的行為，不是新分區功能引入的硬體結論。

5. SerialTransport 不實作共享 serial guard／跨程序 port owner 排他鎖；Session owner
檢查只約束該物件的執行緒。實體執行仍必須走專案規定的 guard、cu/tty aliases owner
檢查和單一測試擁有者，不能因 CLI 只有一條傳送執行緒就省略這些步驟。

6. Linux 輸入目前是 synthetic patterns 或 PPM；--desktop 在 Linux 明確拒絕。
noise 依固定種子與來源 ID 可重播，每幀重新生成，但不是「精確指定比例且確保 RGB565
值不同」的變動測試。沒有把新亂數圖等同 100.000% changed pixels。
本版沒有 Linux 原生桌面擷取、百分比擾動 CLI、會話自動恢復、Windows 或 Rust 新開發。

七、macOS 歷史證據對 Linux 的意義

參考 docs/STATIC_TRANSITION_ASTRA_ANALYSIS_20261011_zh-TW.txt 及
docs/SESSION_STATE_ASTRA_ANALYSIS_20261011_zh-TW.txt。
三秒 static/no-TX 控制正常、六秒 45/60 FPS 恢復首 window ACK timeout 並收到 MSN01；
MSN 在恢復 window 後約 11–16 ms 已讀到，舊 matcher 仍等約兩秒。
隔離診斷在原 timeout 後，以同 fd 嚴格握手加 full 恢復成立；不是本候選版自帶修復。
早先兩個 passive cycle 約 5.114 秒讀到公告等證據支持會話狀態轉換方向，但不證明
精確通用門檻、USB suspend、MCU sleep/reset 或特定 firmware 內部機制。

3840-byte chunks 的第二 window 問題、靜止會話失效與持續移動偶發 timeout 必須分組。
macOS 45、46、…、60 FPS 初掃沒有建立 ACK 失穩 FPS 上限；59/60 的 startup replacement
不能轉述成 60 FPS 硬體極限。Linux 的 chunk60 預設是較保守的起點，不是 Linux 成功證據。
prefix ACK 只有既有 02 03 前綴意義，不可用來證明 LCD 全幅完成或無殘影。

八、最有價值的下一階段實驗與驗收

第一階段先完成原生 Linux 離線門檻。

雜湊；在目標 Linux 執行 build、三組 unit 及完整 PTY，不以 macOS 或 cross-compile 代替。
保留 PTY CSV、stderr/stdout 與 wire／canvas 對照摘要，讓分析者可重算，不只留下 PASS。
原生 CTest 與另行 PTY 均須 exit 0，且每項錯誤注入需確認真正到達預定故障點。

第二階段用可重播來源測完整轉態，而非只用短噪聲進入案例。
至少對三分區×raw/pair×full/diff，比較 keyframe0 與非零；包含低負擔→高負擔→低負擔、
中央不變但兩側變動、first／temporary slow ACK 後恢復、持續慢 ACK、反覆多次進出。
以相同 seed、初始 RGB565、來源 ID 與來源時刻比较四模式；精確比例擾動須不重複抽像素，
並確保改寫後的 RGB565 值不同。另用區域標號／幀號和移動邊界驗證位置，噪聲用於負載。

軟體驗收至少包含：首張全幅；所有 completed wire/window 能對上 CSV；獨立合成畫布
與每區 reference 相符；due=sent+unchanged+skipped+missed_queue+failed（同範圍）；
各次 source gap 的 phase 正確；bands4/halves2 無 intentional skip；center 不主動 skip；
keyframe 到期有全幅 wire；未達安全退出條件時保留模式與 phase，分區內 full 成功後
全部區同步、只原時槽 due/sent +1；
keyframe／探測／後續 patch 失敗後不再送新更新、不提交失敗來源；安全 streak 未足不退出。
瞬間低負載不應使模式抖動；再次變重仍應迅速進入，失敗注入不得靠重跑至通過掩蓋。
