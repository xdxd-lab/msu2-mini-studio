## 最新實機證據

實機測試使用本機凍結候選（App／CLI），以 `e9c5f58` 相同的 tree 建置；凍結檔本身不在 Git 中；兩輪的去識別化日誌見[證據包](evidence/2026-11-17/pack/README.md)。數字是主機送出量，不是 LCD 實際更新率。

| 日期／條件 | 已觀察 | 判讀邊界 |
|---|---|---|
| 11/17 CLI，桌面 Raw 全幅，目標 30 FPS，22 秒 | exit 0；握手失敗、ACK 逾時、傳輸錯誤、重連皆 0。正式窗以 diagnostics 中 session 的 `stream_begin` 時間戳為原點（不是記錄開始時間），取 [+3, +19) 秒；16 秒送 378 幀，約 23.6 幀／秒；每幀 39,018 B，payload 寫入平均約 41 ms，ACK 約 0.9 ms | 單次觀察；桌面像素未固定。部分執行中雜湊與事後輸出缺漏，見證據索引 |
| 11/17 CLI，同上，目標 60 FPS | 同樣無錯誤；同一正式窗送 383 幀，約 23.9 幀／秒。`events.log` 的等待影格取代（`waiting_frames_replaced`）為 793 次（30 FPS 為 141 次），另有 1 次擷取時槽錯過 | 目標加倍沒有提高送出率；每幀約 40 ms 寫入時間與約 24 幀／秒上限相符，但 USB、驅動、裝置或面板的根因未定位 |
| 11/15 GUI，桌面 Raw 全幅 24 FPS，18 秒 | 送出 440 幀，無 ACK 逾時 | GUI 與外層使用不同鎖目錄，不算合格的共用鎖試驗 |
| 11/15 GUI，桌面 Raw 30 FPS | 送出 1584 幀，無 ACK 逾時 | App 本身留在前景、串流長度不受控，不能作 30／60 對照 |
| 11/05 Pair，全幅、目標 24 FPS | 成功 36 幀後下一個 window ACK 等待約 3 秒逾時，RX 0 bytes | 根因未知；之後重新開埠可握手，不代表逾時當下可恢復 |
| 10/31 Pair，全幅、目標 28 FPS | 兩次短測分別成功 50／56 幀後 window ACK 逾時 | 與 11/05 的前兆及 RX 特徵不同，不能當作同一機制 |
| 10/17 素材圖片下載 | 曾完成唯讀下載 | 不代表擦寫、相鄰資料保留或斷電持久性已驗收 |

兩輪 11/17 的共同限制：沒有前景守門，桌面內容未固定；螢幕錄製權限沿用先前狀態，未另行記錄；CLI 結束時印出的 `host_fps=0` 是停止後的快照，不採用；序列埠鎖（flock）的執行中狀態未保存，只有前後 owner 檢查。stdout 的 `dropped` 是來源 frame ID 缺口（見 `controller.hpp` 的 `Snapshot`），與佇列取代定義不同，即使數值相同也不混用。

11/16 曾嘗試以外部瀏覽器視窗作為受控畫面並加上前景守門，因視窗幾何不穩定而在開埠前停止，沒有產生 MSU2 數據；之後的實機短測不再以此為前置。

## 待辦

| 代號 | 問題 | 現況與下一步 |
|---|---|---|
| 01 | Pair ACK 逾時與恢復 | 根因未解。下一步為獨立的 Pair 24 FPS 單輪短測（桌面、全幅、priority off、ACK timeout 3000 ms、不自動重連），首次逾時即停，不重試、不重插、不改 ACK 規則 |
| 02 | 桌面 Raw 30／60 對照 | 11/17 已有單次直接對照（見上表）。重複性、固定內容下的比較與 LCD 端量測仍未做 |
| 03 | 簽章與升版授權 | 本機沒有穩定 Developer ID 身分；ad-hoc 重建後螢幕權限可能需重新授權。短期只使用單一凍結 App |
| 04 | 素材 Flash 寫入 | 未驗收；只曾完成唯讀圖片下載。下一步需指定可犧牲資料，驗證擦除語意、讀回、相鄰資料、取消、備份還原及斷電後持久性；現有離線測試不足以代替 |
| 05 | center3 側區公平性 | 改動已合併，假傳輸測試完成；實機未驗。可用內建 `noise` 來源（每幀全幅變化，使 center3 啟用、左右區持續變動）驗證左右區是否都有送出及最舊區域年齡上限。此方法無法驗證「左動右靜」或動轉靜，也不能代表 LCD 畫面。11/17 一次嘗試在開埠前因權限請求逾時中止，沒有輸出 |
| 06 | 資源與診斷穩健性 | 假傳輸下的診斷故障測試，以及 `e9c5f58` 上 120 秒 ASan／UBSan 資源採樣已完成，threads／FD 在結束後回到起點。ASan 下的記憶體數字不能作洩漏判讀；真實磁碟故障、非 ASan RSS／CPU 與長時間實機測試未驗，不宣稱無洩漏 |
| 07 | close／disconnect 請求邊界 | 程式閱讀發現 close 後清除 disconnect 旗標的位置與 `set_flags` 鎖規則不同；先用受控的重複請求情境確認是否有可見影響，目前未重現問題 |
