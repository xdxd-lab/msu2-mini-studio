send --hold-open-ms 實作與離線證據審核
日期：2026-10-11（Asia/Taipei）

審核結論

本次變更可交付使用者進行 0 秒／10 秒實機觀察；未發現需要阻擋交付的實作問題。
新增參數確實在成功送完 payload 後、SerialTransport 解構關閉之前等待，
等待迴圈沒有序列埠讀写、重新握手或重送影像。既有畫面編碼、更新規劃、
Session::send 與 transport 實作保留。

本結論只確認程式結構、離線 PTY 行為與封裝一致性。沒有判定實機的底部
殘留已修復，也没有把 host write 完成、開窗 ACK 或等候時間視為 LCD 完成確認。
本審核代理只讀程式碼、既存紀錄與封裝；沒有開啟實體序列埠，也沒有執行
send／stream。離線執行證據由主代理指派的 GPT-6 Luna medium 測試代理提供。

實作審核

1. msu2_linux_v0_3/src/main.cpp:59 僅在 send 的 allowed options 加入新旗標。
   第 664 行使用既有 unsigned 整數解析器，預設 0、範圍 0..60000；
   驗證發生在第 666 行建立 SerialTransport 之前。
2. 第 667 行仍只呼叫一次原有 connection() 與 Session::send(encoded)。
   送出失敗時會進入原有例外處理，不會進入成功後等待。
3. 第 668–675 行在 transport 與 session 的同一詞法作用域內等待。
   steady_clock 提供單調 deadline；每段 sleep 最多指定 50 ms 並检查
   既有 lock-free atomic interrupted flag。實際喚醒時間仍受 OS 排程影響。
   SIGINT 在等待中可提早結束，輸出 interrupted=1，return 130 仍會執行
   C++ 區域物件解構，釋放 transport。
4. stdout 分別保存 post_send_hold_requested_ms、post_send_hold_elapsed_ms
   及 interrupted。量測起點在「要求等待時間」stdout flush 之後；它量測
   等待區段，不代表從最後一個 payload byte 到 OS close 的精確總間隔。
5. manual_test_kit/manual_test.py 驗證範圍、為 send 組入旗標、把指定值與
   完整命令寫入 metadata，並把 send launcher timeout 延長相同秒數。
   Guard 仍涵蓋 child.wait 與中斷清理，直到子程序回收才釋放。
   compare_runs.py 增加 hold_open_ms 欄位，便於對照保存的執行設定。
6. README 提供 0／10000 ms 命令，明示先恢復可比較的初始畫面，以及上一輪
   完整色條可能遮掩下一輪未完成傳輸。使用者仍應記錄重新插拔與命令退出時刻。

使用者實機結果的判讀界線

若同一初始畫面的 10 秒組較 0 秒組完整，可支持「保持連線時間影響觀察結果」；
尚不能單獨歸因於主機佇列、裝置處理速度或關閉時的 modem 狀態還原。
若只在命令退出前後發生改變，請保存這個時間關係；transport 關閉前恢復
原始 modem/termios 的行為是既有實作，本輪沒有修改。
若兩組結果一樣，也不能靠此排除其他傳輸或韌體原因。每輪的初始畫面、
1 秒／10 秒觀察、命令退出前後、重新插拔狀況与原始 stdout 都應一起保留。
